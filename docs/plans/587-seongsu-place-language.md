## 목표와 범위

관리자가 등록한 영문 장소 정보를 일반 사용자 조회에 제공합니다. 조회 시 외부 번역 서비스를 호출하지 않습니다. 추후 동적 번역을 도입할 때 사용자 API와 한국어 장소 원본을 유지할 수 있도록 번역 저장을 분리합니다.

| 변경 영역 | 작업 |
| --- | --- |
| 관리자 등록과 수정 | `nameEn`, `addressEn`, `stationEn`을 선택 입력으로 받습니다. 수정 시 생략 또는 `null`은 기존 값을 비웁니다. |
| 관리자 장소 응답 | 한국어 원본과 영문 원본을 함께 제공하고 미등록 영문은 `null`로 반환합니다. |
| `GET /places` | 선택한 언어의 장소 목록을 반환합니다. |
| `GET /main/places/search-location` | 장소 목록 문자열에 언어를 적용하며 마커와 목록의 대상 장소는 유지합니다. |
| `GET /main/places/{placeId}/summary` | 선택한 언어의 단일 요약을 반환합니다. |
| `GET /users/me/favorite-places` | 선택한 언어의 좋아요 장소 목록을 반환합니다. |
| Swagger | 위 입력, 응답과 오류 계약을 실제 코드에 반영합니다. |

일반 조회는 기존 `name`, `address`, `station` 필드를 사용합니다. 영문이 없는 항목만 한국어로 대체합니다. 영문 누락을 이유로 장소를 제외하지 않습니다. 언어 변경으로 노출 조건, 정렬, 좌표, 이미지, 운영 정보, 좋아요 여부와 커서를 바꾸지 않습니다.

장소 주변 게시글 번역, 관리자 통계 API, #577 계정 탈퇴, 동적 번역 호출과 운영 환경 데이터 투입은 이번 구현 범위에서 제외합니다.

## 현재 구현과 변경 지점

`Place`는 한국어 이름, 주소와 역 이름을 저장하고 영문 저장 구조는 없습니다. `PlaceService`가 관리자 등록과 수정, 상세 조회, 홈 목록과 지도 조회를 담당합니다. 좋아요 목록은 `PlaceFavoriteService`에서 조회합니다.

홈 목록은 `PlaceRepositoryImpl`의 native SQL과 `HomePlaceResultSetExtractor`를 사용합니다. 지도와 좋아요 목록은 장소와 운영 일정을 조회한 뒤 요약을 구성합니다. 언어 적용 때문에 기존 노출 및 일정 계산을 재작성하지 않습니다.

변경 대상은 `domain/place`의 Entity와 Repository, 입력 DTO와 Command, 관리자 응답 모델, 네 조회 API의 Controller와 Swagger, 조회 결과 구성 및 관련 테스트입니다. 기존 게시글 번역 테이블은 구조 참고만 하며 장소 번역과 공유하지 않습니다.

## 승인된 저장 구조

`place`에는 한국어 원본을 유지하고, 별도 `place_translation` 테이블에 언어별 문자열을 저장합니다. API의 `nameEn` 같은 고정 필드명과 내부 저장 구조를 분리합니다.

| 컬럼 | 역할 |
| --- | --- |
| `id` | 번역 행의 식별자 |
| `place_id` | 한국어 장소의 외래키이며 필수입니다. |
| `language_code` | 대상 언어이며 이번에는 `EN`을 저장합니다. |
| `translated_name` | 해당 언어의 장소 이름이며 미등록 시 `NULL`입니다. |
| `translated_address` | 해당 언어의 주소이며 미등록 시 `NULL`입니다. |
| `translated_station` | 해당 언어의 역 이름이며 미등록 시 `NULL`입니다. |
| `created_at`, `updated_at` | 저장과 갱신 시각입니다. |

DB에 `UNIQUE(place_id, language_code)`와 장소 FK를 둡니다. JPA에서는 번역이 해당 장소를 참조하도록 하며, 목록 조회에서 번역 컬렉션을 지연 로딩하지 않습니다. 세 영문 값이 모두 미등록이면 해당 언어 행을 제거하고, 일부만 등록되어 있으면 나머지를 `NULL`로 저장합니다.

이번에는 관리자 입력만 저장하므로 번역 공급자, 작업 상태, 재시도 횟수, 원문 해시와 범용 번역 인터페이스를 미리 도입하지 않습니다. 동적 번역 도입 시 같은 언어 행에 결과를 저장할 수 있고, 생성 책임을 별도 서비스로 추가할 수 있습니다. 수동 입력 우선순위, 원문 변경에 따른 결과 무효화, 동시 생성, 실패와 재시도 정책은 당시 합의한 뒤 컬럼과 유스케이스를 확장합니다. 지금 구조가 향후 정책 변경을 모두 무변경으로 수용한다는 의미는 아닙니다.

현재 develop에는 V13까지 있습니다. 새 migration은 구현 시점에 전체 버전을 다시 확인해 다음 빈 버전을 사용합니다. 대기 중인 #577에도 V13과 V14 파일이 있으므로 두 작업의 병합 순서에 따라 버전 충돌을 조정하고, 이미 적용된 migration은 변경하지 않습니다.

## 쓰기와 조회 흐름

### 관리자 쓰기

1. 관리자 권한과 한국어 및 영문 입력, 운영 일정을 검증합니다.
2. 기존 S3 썸네일 처리 흐름을 유지합니다.
3. 같은 DB transaction에서 장소 원본, 일정과 해당 장소의 영문 행을 저장합니다.
4. 수정은 DOCS의 전체 대체 계약을 적용합니다. 영문 값 생략 또는 `null`을 기존 값 유지로 해석하지 않습니다.
5. DB 저장에 실패하면 장소와 영문 행을 함께 rollback합니다. 기존 S3 업로드는 DB rollback으로 되돌아가지 않으므로 기존 처리의 한계와 이번 변경 영향을 검증 결과에 명시합니다.

번역 행의 중복은 DB 고유 제약으로 방어합니다. 동시 관리자 수정은 기존 장소 수정의 동시성 정책을 확인하고, 번역 행 생성 경합으로 부분 저장이 발생하지 않도록 실제 MySQL에서 검증합니다.

### 사용자 조회

1. `language`를 `KO` 또는 `EN`으로 해석하고, 미지원 값은 `PLACE400-INVALID_REQUEST`로 거절합니다.
2. 기존 기준으로 조회할 장소와 순서, 페이지를 결정합니다.
3. 홈 native SQL에는 언어별 번역을 LEFT JOIN하고 기존 projection에 표시 문자열을 반영합니다. 없는 번역은 SQL에서 항목별 원문으로 대체합니다.
4. 지도, 단일 요약과 좋아요 조회는 대상 장소 ID에 대한 번역을 한 번에 조회하거나 기존 조회에 LEFT JOIN합니다. 실제 쿼리를 확인해 경로별 방식을 정하며 장소마다 추가 쿼리를 실행하지 않습니다.
5. 기존 요약 필드에 선택한 문자열을 반환합니다. 조회 경로에는 번역 생성과 DB 쓰기를 추가하지 않습니다.

표시 문자열 선택은 place 도메인에서 처리하고, 번역 저장 방식이 Controller에 드러나지 않도록 합니다. 관리자 원본 조회에는 사용자용 한국어 대체 처리를 적용하지 않습니다.

## 구현 순서

1. 아래 승인된 입력 규칙과 저장 구조를 적용하고, 현재 Controller의 파라미터 변환 및 오류 처리를 확인합니다.
2. migration과 번역 Entity 및 Repository를 추가하고 기존 장소 데이터 보존, FK와 고유 제약을 검증합니다.
3. 관리자 등록과 수정, 원본 조회 모델에 영문 필드를 연결합니다.
4. 네 사용자 조회 API에 언어를 전달하고 번역 조회 및 항목별 한국어 대체를 적용합니다.
5. Swagger를 DOCS 계약과 대조하고 실제 응답 직렬화를 확인합니다.
6. 아래 검증을 실행한 뒤 변경 diff와 결과를 보고합니다. 커밋과 push, PR 생성은 각각 승인을 받은 뒤 진행합니다.

기능 구현 시작은 2026-10-12 사용자 요청으로 승인받았습니다. 개인 자료의 원본이나 식별자 매핑은 저장소에 복사하지 않습니다.

Use Case와 Repository는 실제 MySQL 통합 테스트로 검증합니다. Web 테스트는 저장소 기준에 따라 인증과 인가 계약에 집중하며 입력과 응답 직렬화는 실행 결과와 OpenAPI 확인으로 검증합니다. `spotlessApply`, diff 검토, 전체 `test`를 실행하고 긴 로그는 임시 파일에 보관합니다. 실행하지 않거나 건너뛴 검증은 완료 보고에서 구분합니다.

## 구현 전 검토 항목의 처리 결과

- 영문 입력 규칙과 저장 구조는 아래 구현 승인 결과의 기준으로 확정했습니다.
- 홈 조회는 native SQL LEFT JOIN, 지도와 좋아요 목록은 대상 ID의 번역을 한 번에 조회합니다. 단일 요약과 관리자 원본 조회는 장소 및 언어로 한 건을 조회합니다.
- 기존 영문 자료의 투입은 `sourceId`와 실제 `placeId` 매핑, 대상 환경, 백업 및 재실행 기준을 먼저 확인합니다. 파일의 행 순서나 장소명으로 연결하지 않습니다. 운영 데이터 변경은 별도 승인을 받습니다.
- 동적 번역은 별도 작업입니다. 이번 조회에 DeepL 호출, 자동 번역 fallback 또는 회원 번역 횟수 차감을 넣지 않습니다.

Swagger UI는 `http://localhost:8080/swagger-ui/index.html`입니다. 운영진 장소 등록 또는 수정의 JSON `request` Part에 `nameEn`, `addressEn`, `stationEn`을 추가해 확인합니다.

```json
{
  "nameEn": "Seongsu Cafe",
  "addressEn": "1 Yeonmujang-gil, Seongdong-gu, Seoul",
  "stationEn": "Seongsu Station"
}
```

위 JSON은 영문 필드만 발췌한 예시입니다. 실제 요청에는 기존 필수 한국어 필드와 좌표, 유형, 거리 및 7개 요일 운영 일정을 함께 전달합니다. 수정 요청의 영문 생략은 기존 영문을 제거합니다.

1. 관리자 응답에서 한국어와 영문 원본을 함께 확인합니다.
2. `/places?language=EN`, `/main/places/{placeId}/summary?language=EN`, 지도 조회와 로그인한 회원의 좋아요 목록에서 같은 영문을 확인합니다.
3. 영문 주소만 비우면 영어 조회의 주소만 한국어로 반환되는지 확인합니다.
4. `language`를 생략하면 한국어, `language=en` 또는 `language=`이면 400과 `PLACE400-INVALID_REQUEST`인지 확인합니다.

### 확인한 제약

- 새 DB에 전체 Flyway를 적용하면 기존 V1과 V2의 `ft_notice_title_content` 중복으로 V2가 실패합니다. 기존 migration을 수정하지 않았습니다. V14 업그레이드 테스트는 사용자 요청으로 제거했습니다. 이전에 수행한 독립 업그레이드 검증 이력은 있지만 현재 테스트 모음에는 migration 검증이 포함되지 않습니다.
- 서비스 통합 테스트의 S3는 기존 공통 테스트 설정에 따라 mock입니다. 실제 S3 통신은 검증하지 않았고 DB rollback으로 기존 S3 업로드를 되돌릴 수 없는 한계도 유지됩니다.
- 조회 시 외부 번역 API 호출과 운영 데이터 투입은 하지 않습니다.

- `spotlessApply`, `spotlessCheck`, 전체 `test`, `bootJar`가 모두 성공했습니다.
- 전체 테스트 344개, 실패 0개, 오류 0개, 건너뜀 21개입니다. 추가한 장소 번역 테스트는 7개이며 모두 실행해 통과했습니다. 건너뛴 21개는 `CHAT_TRANSLATION_REDIS_TESTS=true`일 때만 실행하는 기존 채팅 Redis 테스트입니다.
- 임의 포트의 실제 HTTP 서버와 MySQL 및 Redis Testcontainers에서 조회 언어, 관리자 원본 응답, OpenAPI, DB rollback과 동시 수정, 번역 일괄 조회의 쿼리 수를 확인했습니다. 사용자가 직접 실행할 기존 `local` 환경의 데이터와 외부 연동은 검증하지 않았습니다.
- 커밋, push와 PR 생성은 하지 않았습니다.


### 테스트 범위 조정

사용자 검토에 따라 V14 migration 테스트, 조회 테스트에 섞여 있던 OpenAPI assertion과 Hibernate Statistics 쿼리 수 assertion을 제거했습니다. V14 SQL과 실제 기능은 유지합니다. 위 최종 검증 수치는 조정 전 결과이며, 조정 후 `spotlessApply`와 장소 번역 테스트 6개가 모두 통과했고 `git diff --check`도 통과했습니다. 전체 테스트는 이번 조정 후 재실행하지 않았습니다. 조회 테스트는 반환 문자열, 한국어 대체, 기존 장소와 커서 보존을 검증합니다.


### local 프로필 실행 확인

`.secret`의 필요한 설정을 메모리로 읽고 `local` 프로필 서버를 8080 포트에 실행했습니다. 기존 연결과 분리한 확인용 MySQL 및 Redis 컨테이너를 사용했습니다. 로컬 DB는 기존 `ddl-auto=update` 설정으로 생성했으며 Flyway 적용 검증으로 간주하지 않습니다.

- 실제 HTTP 요청으로 목록, 지도와 단일 요약의 영어 응답, 영문 미등록 항목의 한국어 대체, 언어 생략 시 한국어와 잘못된 언어의 400 오류를 확인했습니다.
- local 실행에서는 관리자 수정과 인증이 필요한 좋아요 목록을 다시 확인하지 않았습니다. 해당 기능의 검증 근거는 앞서 수행한 통합 테스트입니다.
- 사용자 요청으로 실행한 서버와 이번에 만든 두 컨테이너 및 임시 볼륨을 종료하고 제거했습니다. 비밀 값과 확인용 데이터는 저장소에 추가하지 않았습니다.
