# DB 및 migration 컨벤션

## 목적

데이터베이스 스키마와 조회 코드를 안전하게 변경하기 위한 기준을 정합니다. 데이터 정합성을 지키면서 조회 목적에 맞는 기술과 구현 방식을 선택해야 합니다.

## 원칙

### 스키마 변경

데이터베이스 스키마는 Flyway migration으로만 변경합니다.

- 이미 적용한 migration 파일은 수정하거나 삭제하지 않습니다.
- 버전 중복 등으로 새 데이터베이스를 생성할 수 없다면 checksum을 임의로 바꾸지 않습니다. 문제가 된 버전을 처리할 방법을 정합니다.
- `ddl-auto=validate`로 애플리케이션 모델과 스키마가 일치하는지 확인합니다.

배포 전에 백업과 롤백 계획을 세웁니다.

- 코드, 이미지, 설정, DB migration은 각각 롤백할 수 있는지 판단합니다.
- 되돌릴 수 없는 migration은 먼저 백업하고 `dev` 환경에서 충분히 테스트합니다.
- 롤백이 어려운 상황에 대비해 forward fix도 함께 계획합니다.

### 제약 조건

데이터 구조와 참조 무결성을 보장하려면 `NOT NULL`, `FOREIGN KEY`, `UNIQUE` 제약 조건을 사용합니다. 애플리케이션에서 같은 값을 먼저 검증하더라도 해당 제약 조건을 생략하지 않습니다.

애플리케이션이 검증하는 비즈니스 규칙은 DB `CHECK` 제약 조건으로 중복해서 정의하지 않습니다. 비즈니스 규칙이 바뀌면 애플리케이션의 검증 로직만 변경합니다.

### 조회 방식

Aggregate 사이의 참조는 ID로 보관합니다. JPA 연관관계는 같은 Aggregate 안에서만 사용합니다.

조회 성격에 맞는 도구를 사용합니다.

- 단순 저장이나 존재 확인에는 JPA Repository를 사용합니다.
- 목록, 정렬, 커서, 집계처럼 복잡한 조회에는 QueryDSL을 사용합니다.
- 조회 Repository는 필요한 Result 또는 Response projection을 바로 반환합니다. 조회만을 위해 Entity 그래프를 조립하지 않습니다.

JPA와 Hibernate는 Entity 매핑, 변경 감지, 영속 시간 기록처럼 영속성을 관리하는 데 사용합니다. 조회 조건, 정렬, 상태별 노출 범위처럼 비즈니스 흐름에 영향을 주는 동작은 ORM의 자동 기능에 맡기지 않습니다.

`@OrderBy`로 컬렉션 정렬을 지정하지 않습니다. Repository 쿼리나 QueryDSL의 `orderBy`에 정렬 기준을 명시합니다.

자동 Soft Delete 필터를 사용하지 않습니다. 일반 조회의 활성 상태 조건과 삭제 데이터를 포함하는 조회 조건을 Repository 메서드나 QueryDSL에 각각 명시합니다.

QueryDSL로 작성한 조회가 실행될 SQL의 조건과 의도를 오히려 이해하기 어렵게 만든다면 native SQL을 검토합니다. 데이터베이스 전용 함수, 복잡한 집계, 윈도우 함수처럼 SQL로 직접 표현할 때 조회 의도가 더 분명해지는 경우에 사용할 수 있습니다. PR에 QueryDSL 대신 native SQL을 선택한 이유를 기록하고 MySQL 통합 테스트로 쿼리와 결과 매핑을 검증합니다.

`@EntityGraph`처럼 조회 범위나 실행 쿼리에 영향을 주는 JPA 기능은 QueryDSL과 비교한 선택 근거를 확인한 뒤 도입합니다.

성능에 영향을 주는 변경은 근거를 확인하고 적용합니다. 인덱스, 쿼리, locking을 바꿀 때는 실행 계획이나 측정 결과를 함께 검토합니다.

#### 조회 조건과 도메인 규칙

QueryDSL의 `where` 절이 도메인 객체에 있는 규칙을 다시 표현해야 한다면, 먼저 도메인 로직을 재사용할 수 있는지 검토합니다. 같은 규칙을 두 곳에 표현하면 변경할 때 서로 다른 결과를 낼 수 있으므로 도메인 로직 재사용을 우선합니다.

다만 중복을 없애기 위해 다음과 같은 우회 방법을 사용하지 않습니다.

- 조회 범위를 불필요하게 넓힙니다.
- 조회한 데이터를 애플리케이션에서 다시 필터링합니다.
- 영속성 계층의 관심사를 도메인 객체에 노출합니다.
- 쿼리 성능이나 인덱스 사용을 악화시킵니다.

도메인 로직 재사용과 쿼리 조건의 중복 표현 중 하나를 선택할 때는 데이터 정합성, 쿼리 성능, 코드 가독성, 변경 가능성, 테스트 비용을 함께 검토합니다. 어느 한쪽이 항상 우선한다고 가정하지 않습니다.

중복 표현이 더 적절하다고 판단했다면 선택 근거와 두 로직의 일관성을 검증하는 방법을 PR에 기록합니다.

### DB 작업 테스트

- Repository와 QueryDSL은 실제 MySQL Testcontainers 환경에서 테스트합니다.
- 테스트용 계정, 권한, 민감한 운영 데이터는 코드나 문서에 적지 않습니다.
- DB 인증 정보는 Secret 관리 체계로 주입합니다. Git, 이미지, 로그에는 포함하지 않습니다.

### 테이블 이름

테이블 이름은 소문자 단수형으로 작성합니다. ORM과 매핑할 때는 `@Table`에 테이블 이름을 명시합니다.

## 범위

이 컨벤션은 DB 스키마, Flyway migration, JPA Repository, QueryDSL 조회 코드에 적용합니다.

외부 저장소나 검색 엔진처럼 데이터베이스가 아닌 저장 기술에는 해당 기술의 제약을 우선 적용합니다. 도메인 규칙의 위치와 책임은 [Domain Boundaries](domain-boundaries.md) 문서를 따릅니다.

## 필요한 예시

도메인 객체의 공개 여부 판단과 QueryDSL의 조회 조건이 같은 규칙을 표현한다고 가정합니다. 도메인 로직을 재사용하려고 모든 데이터를 조회한 뒤 애플리케이션에서 필터링해야 한다면, QueryDSL에 조건을 표현하고 두 규칙의 일관성을 테스트하는 편이 적절합니다.

테이블 이름은 다음과 같이 명시합니다.

```java
@Table(name = "post")
public class Post {
}
```

## 팀 논의가 필요한 규칙

다음 상황에서는 구현 전에 팀원과 논의합니다.

- 도메인 로직과 조회 조건에 같은 규칙을 중복해서 표현해야 합니다.
- 적용한 migration을 되돌릴 수 없습니다.
- 같은 Aggregate 밖의 Entity에 JPA 연관관계를 설정해야 합니다.
