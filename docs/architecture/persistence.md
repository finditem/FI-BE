# DB 및 migration 컨벤션

DB 스키마, Flyway migration, JPA Repository와 QueryDSL에 적용합니다. 다른 저장 기술은 해당 기술의 제약을 따릅니다.

## 원칙

### 스키마 변경

데이터베이스 스키마는 Flyway migration으로만 변경합니다.

- 이미 적용한 migration 파일은 수정하거나 삭제하지 않습니다.
- 버전 중복 등으로 새 데이터베이스를 생성할 수 없다면 checksum을 임의로 바꾸지 않습니다. 문제가 된 버전을 처리할 방법을 정합니다.
- `ddl-auto=validate`로 애플리케이션 모델과 스키마가 일치하는지 확인합니다.

배포 전에 백업과 롤백 계획을 세웁니다.

- 코드, 이미지, 설정, DB migration은 각각 롤백할 수 있는지 판단합니다.
- 되돌릴 수 없는 migration은 먼저 백업하고 `dev` 환경에서 충분히 테스트합니다.
- 롤백이 어려운 상황에 대비해 forward fix도 함께 계획합니다.

### 제약 조건

데이터 구조와 참조 무결성을 보장하려면 `NOT NULL`, `FOREIGN KEY`, `UNIQUE` 제약 조건을 사용합니다. 애플리케이션에서 같은 값을 먼저 검증하더라도 해당 제약 조건을 생략하지 않습니다.

비즈니스 검증은 애플리케이션에 두고 DB `CHECK`에 중복 정의하지 않습니다.

### 조회 방식

요구사항과 비즈니스 명세를 구성할 때 연관된 객체의 의미와 사용 범위를 먼저 확인합니다. 다른 객체의 ID 식별자만 참조하면 되는 경우에는 ID 값만 보관하고 JPA 연관관계를 설정하지 않습니다. 그 외에는 객체 간 관계를 Entity의 JPA 연관관계로 표현합니다.

JPA 연관관계를 사용하면 Fetch Join, EntityGraph, batch fetch 등 조회 목적에 맞는 방법을 선택해 N+1 쿼리와 불필요한 데이터 로딩을 방지합니다. 연관관계의 기본 fetch 전략에 조회 동작을 맡기지 말고, 실제 쿼리와 로딩 범위를 확인합니다. 조회에 필요한 연관 데이터는 조회 쿼리에서 명시적으로 연결합니다.

조회 성격에 맞는 도구를 사용합니다.

- 단순 저장이나 존재 확인에는 JPA Repository를 사용합니다.
- 목록, 정렬, 커서, 집계처럼 복잡한 조회에는 QueryDSL을 사용합니다.
- QueryDSL 조회는 필요한 필드만 DTO 또는 record로 직접 projection해 Repository에서 반환합니다. 기존 프로젝트의 결과 타입 이름과 책임을 따르며, 조회 결과를 전달하기 위해 Entity 그래프를 조립하지 않습니다.

JPA와 Hibernate는 Entity 매핑, 변경 감지, 영속 시간 기록처럼 영속성을 관리하는 데 사용합니다. 조회 조건, 정렬, 상태별 노출 범위처럼 비즈니스 흐름에 영향을 주는 동작은 ORM의 자동 기능에 맡기지 않습니다.

`@OrderBy`로 컬렉션 정렬을 지정하지 않습니다. Repository 쿼리나 QueryDSL의 `orderBy`에 정렬 기준을 명시합니다.

자동 Soft Delete 필터를 사용하지 않습니다. 일반 조회의 활성 상태 조건과 삭제 데이터를 포함하는 조회 조건을 Repository 메서드나 QueryDSL에 각각 명시합니다.

QueryDSL 코드가 복잡해져 조회 조건과 결과를 이해하는 데 병목이 생기거나, DB 전용 함수·복잡한 집계·윈도우 함수처럼 SQL로 조회 의도가 더 명확하면 native SQL을 사용할 수 있습니다. native SQL을 선택한 경우 그 이유와 쿼리의 의도를 작업 보고에서 설명하고, MySQL 통합 테스트로 쿼리와 결과 매핑을 검증합니다.

`@EntityGraph`처럼 조회 범위나 실행 쿼리에 영향을 주는 JPA 기능은 QueryDSL과 비교한 선택 근거를 확인한 뒤 도입합니다.

성능에 영향을 주는 변경은 근거를 확인하고 적용합니다. 인덱스, 쿼리, locking을 바꿀 때는 실행 계획이나 측정 결과를 함께 검토합니다.

#### 조회 조건과 도메인 규칙

목록, 검색과 집계의 조회 조건은 Repository의 QueryDSL 또는 SQL 쿼리에 명시합니다. 필요한 데이터는 JOIN으로 연결하고, QueryDSL은 필요한 필드를 DTO 또는 record에 직접 projection해 반환합니다. 노출 상태와 필터 조건은 `where` 절에 표현합니다. 도메인 객체에 같은 판단이 있더라도 객체 메서드를 재사용하기 위해 조회 결과를 애플리케이션에서 다시 거르지 않습니다.

조회 조건을 작성할 때 다음과 같은 우회 방법을 사용하지 않습니다.

- 조회 범위를 불필요하게 넓힙니다.
- 조회한 데이터를 애플리케이션에서 다시 필터링합니다.
- 영속성 계층의 관심사를 도메인 객체에 노출합니다.
- 쿼리 성능이나 인덱스 사용을 악화시킵니다.

상태 변경과 업무 검증에 필요한 규칙은 해당 도메인의 책임으로 둡니다. 같은 업무 조건이 조회와 상태 변경에 모두 필요하면 조회 쿼리와 도메인 규칙에 각각 표현하고, 경계값과 상태 조합을 테스트해 결과가 일치하는지 확인합니다. 정책 자체가 불분명하거나 두 결과가 다르면 구현 전에 팀과 논의합니다.

### DB 작업 테스트

- Repository와 QueryDSL은 실제 MySQL Testcontainers 환경에서 테스트합니다.
- 테스트용 계정, 권한, 민감한 운영 데이터는 코드나 문서에 적지 않습니다.
- DB 인증 정보는 Secret 관리 체계로 주입합니다. Git, 이미지, 로그에는 포함하지 않습니다.

### 테이블 이름

테이블 이름은 소문자 단수형으로 작성합니다. ORM과 매핑할 때는 `@Table`에 테이블 이름을 명시합니다.

도메인 규칙의 책임은 [Domain Boundaries](domain-boundaries.md)를 따릅니다.

## 필요한 예시

게시글 목록 조회는 [`PostRepositoryImpl`](../../src/main/java/com/fmi/domain/post/repository/PostRepositoryImpl.java)처럼 삭제 여부와 필터를 `where`에 명시하고, 즐겨찾기 데이터가 필요하면 JOIN으로 연결합니다. 조회 결과를 만든 뒤 도메인 메서드로 다시 필터링하지 않습니다.

테이블 이름은 다음과 같이 명시합니다.

```java
@Table(name = "post")
public class Post {
}
```

## 팀 논의가 필요한 규칙

다음 상황에서는 구현 전에 팀원과 논의합니다.

- 조회 조건과 상태 변경 규칙의 기대 결과가 다르거나 정책이 불분명합니다.
- 적용한 migration을 되돌릴 수 없습니다.
- ID만으로 참조할 수 있는지 또는 객체 간 JPA 연관관계가 필요한지 요구사항만으로 판단하기 어렵습니다.
