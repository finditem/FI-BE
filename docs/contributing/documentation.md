# 문서 컨벤션

## 문서 관리

- 백엔드 팀원은 팀 논의와 승인을 거쳐 문서를 수정합니다.
- 컨벤션은 영역별 overview에서 연결합니다.
- 같은 규칙은 원본 문서 한곳에서 관리하고, 다른 문서에서는 해당 섹션을 링크합니다.

## 지침 작성 원칙

- 지켜야 할 규칙, 적용 조건과 예외만 작성합니다. 당위, 배경과 기대 효과는 생략합니다.
- 의미가 겹치는 문장과 항목은 통합합니다. 문장, 표, 예시로 같은 내용을 반복하지 않습니다.
- 예시만으로 규칙이 명확하면 설명 없이 예시만 둡니다. 예시에 드러나지 않는 조건과 예외는 짧게 덧붙입니다.
- 업계에서 통용되는 용어로 긴 설명을 대체합니다. 팀 고유 용어나 뜻이 모호한 용어만 정의합니다.
- 대상, 조건, 책임, 금지 사항과 승인 절차는 축약 과정에서 누락하지 않습니다.
- 구현 사례와 가상 예시를 구분합니다. 실제 구현은 파일 경로를 연결하고, 가상 예시는 현재 정책으로 단정하지 않습니다.
- 변경 이력과 작업 과정은 Issue와 PR에 기록합니다.

## 형식

### 제목과 구성

제목에는 순번을 쓰지 않습니다. 번호 목록은 절차에만 사용합니다.

```md
# 사용자 인증

## 설정 절차

1. 인증 정보를 설정합니다.
2. 요청을 전송합니다.
```

제목은 내용에 맞게 정하고 빈 항목은 생략합니다. 팀 논의가 필요한 규칙은 문서 마지막에 둡니다.

### 코드 표기

식별자와 입력값은 인라인 코드로, 여러 줄 예시는 언어를 지정한 코드 블록으로 작성합니다. 인라인 코드에 굵은 글씨를 겹치지 않습니다.

```md
`POST /users`를 호출합니다.
환경 변수 `API_KEY`를 설정합니다.
```

### 예시

변경 전후 비교가 필요하면 같은 대상과 조건으로 `적용 전`, `적용 후`를 제시합니다. 권장 형태만으로 충분하면 해당 예시만 둡니다.

```java
// 비권장
orderNumberGenerator.generateOrderNumber();

// 권장
orderNumberGenerator.generate();
```

### 문장 작성

- 본문은 존댓말로 통일합니다. 예시 코드의 식별자와 문자열은 기존 표기를 유지합니다.
- 작업 지시는 독자를, 시스템 동작은 시스템을 주어로 씁니다. 능동형과 직접적인 동사를 사용합니다.
- 한 문장에는 하나의 규칙을 담습니다. 짧은 규칙은 목록이나 표로 정리합니다.
- `적절히`, `필요시`, `관련 내용` 대신 대상과 조건을 명시합니다.
- 수치, 임계값, 시간과 환경은 확인된 값만 적습니다.
- 같은 개념에는 같은 용어를 사용하고, 기술과 제품명은 공식 표기를 유지합니다.
- 익숙한 기술 용어와 약어는 풀어 쓰지 않습니다.
- 가운데점 대신 쉼표, 접속사 또는 줄바꿈을 사용합니다.

## 검토

- 중복 설명과 불필요한 이유를 제거했습니까?
- 예시가 전달하는 내용을 본문에서 반복하지 않았습니까?
- 통용 용어로 대체할 수 있는 장황한 표현이 남았습니까?
- 적용 조건, 예외, 책임과 승인 절차를 유지했습니까?
- 원본 문서와 구현 경로의 링크가 유효합니까?
