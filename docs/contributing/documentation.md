# 문서 컨벤션
## 문서 관리

### 권한

백엔드 팀원 누구든 해당 문서를 수정할 수 있습니다.

팀원의 승인 없이 업데이트하지 않습니다.

### 논의

문서 수정 전 논의가 필요합니다. Slack 등 메신저를 통해 팀원과 충분한 상의 후 수정 해주세요.


## 컨벤션

다양한 오픈소스의 Contribute 규칙을 참고했습니다.

### 제목
제목에는 순번을 쓰지 않습니다. 제목 수준과 문서 내 배치 순서로 문서 구조를 나타냅니다.

절차나 작업 순서가 필요한 경우에만 본문에서 순서 있는 목록을 사용합니다.

```md
# 사용자 인증

## 목적

## 요구사항
1. 인증 정보를 설정합니다.
2. 요청을 전송합니다.
```

### 컨벤션 문서 형식

컨벤션 문서는 `docs/`의 영역별 overview에서 찾아갈 수 있게 배치합니다. 독자가 판단할 기준을 먼저 제시하고, 혼동되는 선택에는 적용 전후 코드나 설정 예시와 실제 구현 경로를 붙입니다. 제목은 내용에 맞게 정하고 적용할 내용이 없는 항목은 생략합니다.

- `기준`: 반드시 지켜야 하는 규칙과 적용 조건을 짧게 작성합니다.
- `예시`: 판단이 어려운 곳에 적용 전후 코드, SQL 또는 테스트를 같은 조건으로 보여줍니다.
- `근거`: 가능하면 실제 FI-BE 코드나 테스트 경로를 연결합니다.
- `팀 논의가 필요한 규칙`: 문서의 마지막에 둡니다. 합의한 내용은 예외로 적용하거나 원본 문서를 갱신합니다.

```md
# [문서 제목]

짧은 기준과 적용 범위

## 판단 기준

## 적용 전후 예시

## 팀 논의가 필요한 규칙
```

### 코드 표기
코드, 명령어, 파일명, API 경로, 설정값처럼 정확하게 입력하거나 식별해야 하는 값은 인라인 코드로 표기합니다.

여러 줄의 코드, 명령어, 설정 예시는 코드 블록으로 작성합니다. 코드 블록에는 가능한 한 언어 또는 형식을 지정합니다.

`POST /users`를 호출합니다.

설정 파일은 `config.yml`입니다. 환경 변수 `API_KEY`를 설정합니다.

```bash
npm run build
{
  "enabled": true
}
```

인라인 코드와 굵은 글씨를 함께 사용하지 않습니다. 코드 영역 안에는 Markdown 서식을 사용하지 않습니다.

### 예시

기능 변경 사항을 설명할 때는 `적용 전`과 `적용 후`를 함께 제시합니다.

- 적용 전에는 기존 동작을 작성합니다.
- 적용 후에는 변경된 동작을 작성합니다.
- 두 항목은 같은 조건과 대상을 비교할 수 있도록 작성합니다.
- 적용 후에는 변경 결과만 작성합니다. 개선 과정이나 불필요한 설명은 포함하지 않습니다.

**적용 전**
```md
이 API를 호출할 때 요청 헤더를 포함해야 하며, 올바른 인증 정보를 제공해야 정상적으로 응답을 받을 수 있습니다.
```

**적용 후**
```md
이 API를 호출할 때 요청 헤더와 인증 정보를 포함하세요.
```

### 문장 작성

토스의 테크니컬 라이팅 가이드에 'Step 3. 문장 다듬기'를 참고합니다.

[Step 3. 문장 다듬기 - toss technical writing guid](https://technical-writing.dev/sentence/index.html)

#### 문장의 주체를 분명하게 하기

출처: [문장의 주체를 분명하게 하기](https://technical-writing.dev/sentence/subject.html)

- 독자가 수행할 작업은 독자의 행동을 중심으로 설명합니다.
- 도구, 기술, 시스템을 행동의 주체로 쓰지 않습니다.
- 시스템 자체의 동작을 설명해야 할 때는 시스템을 주어로 쓸 수 있습니다.
- 수동형보다 능동형을 사용합니다.

```md
<!-- 피해야 할 표현 -->
애플리케이션이 실행되기 전에 설정이 완료되어야 합니다.

<!-- 권장 표현 -->
애플리케이션을 실행하기 전에 설정을 완료하세요.
```

#### 필요한 정보만 남기기

출처: [필요한 정보만 남기기](https://technical-writing.dev/sentence/compactness.html)

- 문장을 짧고 간결하게 작성합니다.
- 한 문장에는 하나의 생각만 담습니다.
- 문장이 길어지면 문장을 나눕니다.
- 핵심 메시지를 보조할 뿐 의미를 더하지 않는 메타 담화를 줄입니다.
  - 문서 흐름을 설명하는 표현: `다음으로`, `앞서 설명했듯이`, `이제 알아보겠습니다`
  - 불필요한 강조 표현: `사실은`, `솔직히 말하면`, `결론적으로`
  - 독자의 반응을 유도하는 표현: `아시겠지만`, `여러분도 아실 것입니다`

```md
<!-- 피해야 할 표현 -->
앞에서 설명했지만, 결론은 이 설정을 변경하는 것이 가장 효과적인 방법이라는 겁니다.

<!-- 권장 표현 -->
이 설정을 변경하는 것이 가장 효과적인 방법입니다.
```

#### 구체적으로 쓰기

출처: [구체적으로 쓰기](https://technical-writing.dev/sentence/concreteness.html)

- `진행`, `수행`, `처리`처럼 의미가 흐릿한 명사형 표현보다 동사를 사용합니다.
- `일부`, `가능성이 있습니다`, `많을 때`처럼 모호한 표현 대신 정확한 조건과 결과를 씁니다.
- 누가, 무엇을, 어디에, 어떻게 하는지 필요한 정보를 문장에 포함합니다.
- 기술 용어나 관용 표현을 그대로 옮기지 말고, 실제 동작을 설명합니다.
- 수치, 임계값, 시간, 대상 환경처럼 판단 기준을 구체적으로 제시합니다.
- 다른 문서, 단계, 변수, 설정값을 참조할 때는 출처와 사용 맥락을 함께 설명하거나 링크합니다.

```md
<!-- 피해야 할 표현 -->
데이터가 많을 때는 성능이 저하될 수 있습니다.

<!-- 권장 표현 -->
데이터가 10,000건을 넘으면 응답 시간이 1초 이상 걸립니다.
```

#### 자연스러운 한국어 표현 쓰기

출처: [자연스러운 한국어 표현 쓰기](https://technical-writing.dev/sentence/natural-kor-expression.html)

- 의미를 더하지 않는 한자어를 제거합니다.
- `수행하다`, `실행하다`, `진행하다`처럼 동작을 흐리는 표현은 가능한 한 직접적인 동사로 바꿉니다.
- 영어식 명사형 표현을 그대로 번역하지 않고, 한국어의 자연스러운 동사 표현으로 씁니다.

```md
<!-- 피해야 할 표현 -->
로그 파일을 삭제하는 작업을 수행합니다.

<!-- 권장 표현 -->
로그 파일을 삭제합니다.
```

#### 일관되게 쓰기

출처: [일관되게 쓰기](https://technical-writing.dev/sentence/consistency.html)

- 기술 용어, 제품명, 도구명은 공식 문서의 표기를 따릅니다. 대소문자도 유지합니다.
- 같은 개념에는 문서 전체에서 하나의 표현만 사용합니다.
- 약어는 처음 등장할 때 전체 이름과 함께 표기합니다. 이후에는 약어를 사용합니다.
- 외래어는 맞춤법뿐 아니라 독자의 익숙함과 업계의 일반적인 사용도 고려해 표기합니다.

```md
<!-- 피해야 할 표현 -->
이 기능은 SSR을 지원합니다.

<!-- 권장 표현 -->
이 기능은 서버 사이드 렌더링(Server-Side Rendering, SSR)을 지원합니다.
```
