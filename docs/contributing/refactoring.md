# 리팩터링

리팩터링 전후에 업무 결과, 오류와 외부 효과가 같아야 한다. 구조 변경 이유와 검증 범위를 먼저 적는다.

## 1. 유지할 계약을 적는다

```text
As-is: Service가 여러 업무 단계를 한 클래스에 표현한다.
To-be: 독립 책임이 확인된 조회 또는 검증을 internal 클래스로 분리한다.
유지: 요청 결과, DB 변경, transaction 경계, 오류 코드, 외부 호출 순서.
```

이 예시는 분리 검토 방법이다. `internal` 도입 시점과 분리 기준은 [Domain Boundaries](../architecture/domain-boundaries.md)의 팀 논의 항목을 따른다. 메서드 수만으로 class를 늘리지 않는다.

## 2. 영향 경계를 확인한다

`web`, `service`, `data`, `repository`, `external` 사이에서 DTO나 영속 객체가 다른 책임으로 새어 나가지 않는지 본다. JPA 관계와 QueryDSL 조건이 달라지면 실행 결과와 성능을 함께 확인한다. 사용하지 않는 추상화를 새로 도입하지 않는다.

## 3. 동작을 검증한다

가장 위험한 변경에 맞춰 [Testing](testing.md)의 단위 또는 통합 테스트를 고른다. 단순 이동을 증명하려고 구현을 그대로 따라 하는 테스트는 추가하지 않는다. 데이터나 외부 효과의 순서가 바뀌면 리팩터링 범위를 벗어날 수 있으므로 사용자에게 먼저 알린다.
