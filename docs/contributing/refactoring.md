# 리팩터링

## 적용 기준

| 작업 | 적용 기준 |
| --- | --- |
| 기존 레거시 기능 수정과 추가 | 해당 영역의 명명, 구조와 호출 스타일 유지 |
| 새 도메인과 새 Use Case 생성 | 프로젝트 가이드 적용 |
| 새 코드에서 기존 레거시 도메인 호출 | 레거시 접점의 기존 호출 방식 유지 |
| 리팩터링 목적의 작업 | E2E 회귀 테스트 확보 후 Use Case 전체를 가이드에 따라 재작성 |

기능 작업에 부분적인 컨벤션 정리와 리팩터링을 섞지 않습니다. 새 코드의 레거시 호출을 위해 기존 도메인까지 재구성하지 않습니다. 도메인 소유권과 호출 권한은 [Domain Boundaries](../architecture/domain-boundaries.md)를 따릅니다.

## 진행 순서

1. 기존 Use Case의 E2E 회귀 테스트를 확보합니다.
2. 진입점부터 결과까지 비즈니스 로직 흐름을 파악합니다.
3. 불명확한 정책과 동작은 사용자 또는 팀과 확정합니다.
4. 객체 간 메시지, 책임과 실행 경계를 정리합니다.
5. 합의한 Use Case 전체를 프로젝트 가이드에 따라 재작성합니다.
6. 동일한 회귀 테스트로 변경 전후 결과를 검증합니다.
7. 운영 위험이 큰 경우에만 Feature Flag로 점진 전환합니다.

## E2E 회귀 테스트

외부 진입점부터 최종 응답, 저장 상태와 외부 부수 효과까지 기존 동작을 검증합니다.

- 성공, 거절, 예외와 실패 후 상태
- 권한, 상태 전이와 경계값
- 해당 Use Case의 중복 요청과 동시성
- 트랜잭션 commit과 rollback, 외부 호출 결과

메서드 호출 횟수만 확인하는 테스트로 E2E 회귀를 대신하지 않습니다. 단위 및 통합 테스트는 [Testing](testing.md)에 따라 위험한 경계를 보완합니다. 테스트가 관찰하지 않은 외부 프로토콜이나 동시성을 검증했다고 보고하지 않습니다.

## 흐름과 경계

```text
입력 -> Controller / Listener -> Service
     -> 검증과 상태 변경 -> Repository / QueryDSL
     -> DB와 외부 연동 -> 응답과 최종 상태
```

| 확인 항목 | 기록할 내용 |
| --- | --- |
| 업무 흐름 | 조건, 분기, 처리 순서와 결과 |
| 메시지 | 호출 주체와 대상, 인자, 반환값, 이벤트와 오류 |
| 도메인 경계 | 데이터 owner, read/write와 도메인 간 호출 |
| 트랜잭션 | 시작과 종료, lock, commit과 rollback |
| 외부 연동 | 호출 순서, 멱등성, 재시도와 실패 후 상태 |
| 최종 방어선 | DB 제약과 조건부 변경 |

불명확한 내용은 [미확정 정책 처리](../../AGENTS.md#문서에-없는-정책)를 따릅니다. 현재 동작과 확정 정책이 다르면 차이를 먼저 확정합니다. 업무 결과나 API 계약 변경은 리팩터링과 구분합니다.

## Use Case 전체 재작성

- 합의한 Use Case의 비즈니스 로직 전체를 재작성합니다. 일부 클래스나 메서드만 새 스타일로 바꾸지 않습니다.
- 관련 없는 Use Case와 공유 레거시까지 변경 범위를 넓히지 않습니다.
- 레거시 도메인 접점은 기존 호출 방식을 유지합니다.
- 구조와 책임은 [Domain Boundaries](../architecture/domain-boundaries.md), DB와 조회는 [Persistence](../architecture/persistence.md), 표현은 [Code Style](code-style.md)을 따릅니다.
- `internal` 도입과 도메인 분리 등 팀 논의 항목은 구현 전에 합의합니다.
- SQL 조건, 데이터 정합성, 트랜잭션과 외부 효과의 의미를 유지합니다. 쿼리 변경 시 실행 결과와 성능도 확인합니다.
- 사용하지 않는 추상화와 구현을 복제하는 테스트는 추가하지 않습니다.

## 운영 전환

운영 데이터 정합성, 인증이나 외부 부수 효과에 위험이 큰 재작성은 Feature Flag를 사용합니다. 그 외에는 도입하지 않습니다.

```text
Feature Flag OFF -> Legacy Use Case
Feature Flag ON  -> New Use Case
```

- 요청마다 한 경로만 실행합니다.
- 초기에는 Legacy 경로를 유지하고 합의한 대상과 트래픽 범위부터 New 경로를 활성화합니다.
- 전환 전 두 경로의 데이터 계약, 복귀 조건과 관찰 지표를 정합니다.
- 이상이 발생하면 Flag로 Legacy 경로로 복귀합니다. 이미 발생한 DB 변경과 외부 효과는 Flag 전환으로 되돌아가지 않습니다.
- 운영 검증 완료 후 합의한 시점에 Flag와 Legacy 경로를 제거합니다.
